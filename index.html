为什么竞品没做"需求对齐"？

1. 技术难度：需要对话式 AI，传统关键词匹配不够

2. 用户习惯：HR 习惯了"搜 JD 模板"，需要教育市场

3. 商业模型：SaaS 追求"全流程覆盖"，单点功能不够吸引付费

4. 数据壁垒：需要行业 JD 数据库 + 胜任力模型

市场定位

低复杂度 · 单点极致 · 专注需求对齐

不做全流程，做第一个信息转换点

差异化壁垒

LLM 对话能力 + 行业 JD 数据库 + 胜任力模型

竞品需要从零开始建设

03 · 方案定义

产品定义：JD Copilot

"不是帮你写 JD（模板化），而是帮你搞清楚要什么样的人（对话式）。不是帮你筛简历（下游），而是帮你定义筛选标准（上游）。"

✅ MVP 做什么

• 对话式需求收集（AI 追问 + HR 确认）

• 结构化需求文档输出

• JD 草稿生成（行业数据 + 需求文档）

• JD 质量评估（覆盖度 + 同行对比）

成功标准：从"我要一个前端"到拿到 JD ≤ 15 分钟

❌ MVP 不做什么

• 不做简历筛选（下游问题，竞品已覆盖）

• 不做 ATS 集成（V2 再考虑）

• 不做候选人沟通（独立场景）

• 不做批量处理（先做好单次体验）

边界原则：单点极致，不做全流程

Skill Card 六维框架

维度定义
Intent帮 HR 把模糊需求转化为结构化岗位要求，减少 JD 与真实需求的错配

05 · 技术架构

为什么是 Plan-and-Solve + Reflection？

范式选型决策（Hello-Agents Chapter 4）

范式适用性理由
ReAct⭐⭐JD 生成不需要外部工具调用，不需要实时搜索
Plan-and-Solve⭐⭐⭐⭐先收集需求再生成 JD，典型的"先规划后执行"
Reflection⭐⭐⭐⭐⭐JD 质量要求高，需要自校验防止幻觉

Agent 执行流程

Phase 1 — Plan（需求收集）
  AI 对话引导 HR 收集需求
  输出：结构化需求文档

Phase 2 — Solve（JD 生成）
  基于需求 + 行业数据生成 JD
  输出：JD 草稿

Phase 3 — Reflect（质量校验）
  自检查：是否有未确认的要求？
  输出：质量评估报告

幻觉防控（Hello-Agents Chapter 9）

风险措施
编造未提及要求标注来源（"来自对话"或"来自参考"）
编造行业数据只引用 RAG 检索的真实 JD
格式漂移6 层 JSON 兜底 + Few-shot
上下文丢失关键信息每轮带上 + 外部笔记

上下文工程：GSSC 流水线（Gather-Select-Structure-Compress）

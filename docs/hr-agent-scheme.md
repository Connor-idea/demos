## 一、方案概述

### 1.1 一句话定位

**帮 HR 从"用人部门说我要一个前端"开始，通过 AI 对话搞清楚真实需求，生成一份靠谱的 JD。**

### 1.2 为什么不是"简历筛选"

在深入调研了 HR 招聘的完整链路后，我发现简历筛选只是招聘漏斗的下游环节。真正的根因问题是：

> **JD 与用人部门真实需求的错配，是后续所有问题的源头。**

JD 不对 → 筛选标准不对 → 来的人不对 → 面试被否 → 招来了也留不住。

### 1.3 方案价值主张

| 维度 | 当前状态 | 使用 Agent 后 |
|------|----------|-------------|
| JD 编写时间 | 2-4 小时（搜同行 JD + 人工拼凑） | 15-30 分钟（AI 对话 + 人工确认） |
| JD 准确度 | 依赖 HR 个人经验，波动大 | 结构化追问确保覆盖关键维度 |
| 需求对齐 | 靠口头沟通，容易遗漏 | AI 引导式提问，系统性收集 |
| 可追溯性 | 无记录 | 完整对话记录 + 结构化需求文档 |

## 二、问题定义（WHY）

### 2.1 用户画像

**主要用户**：中型企业（100-500 人）的招聘经理 / HRBP
- 每月处理 10-30 个岗位需求
- 每个岗位需要和用人部门沟通需求、编写 JD、发布、筛选
- 经验丰富但面对模糊需求时缺乏结构化工具

**次要用户**：用人部门负责人
- 通常只给出职位名称，没有详细需求
- 对候选人的期望往往是模糊的（"我要一个厉害的人"）

### 2.2 核心痛点（基于真实 HR 经验）

**痛点来源**：与 3 位 HR 从业者的深度访谈 + 招聘平台公开报告

**痛点 1：JD 编写是"猜谜游戏"**
- 用人部门说"我要一个前端工程师"
- HR 只能去招聘平台搜同行 JD，提取"最严苛标准"
- 加上公司特殊描述，拼凑出一份 JD
- **问题**：JD 可能与真实需求严重不符

**痛点 2：需求沟通效率低**
- HR 和用人部门的沟通通常是"你想要什么样的人？"
- 回答往往是模糊的（"技术好的"、"有经验的"）
- 缺乏结构化的追问框架

**痛点 3：JD 质量不可控**
- 不同 HR 写的 JD 质量差异大
- 没有标准化的 JD 质量评估方法
- 用人部门对 JD 的反馈往往是"不够准确"但说不出哪里不对

## 三、解决方案（WHAT）

### 3.1 产品定义

**产品名称**：JD Copilot（JD 副驾驶）

**一句话定义**：通过 AI 对话式交互，帮 HR 从模糊需求出发，系统性收集用人部门的真实需求，生成结构化 JD。

**MVP 范围**：
- ✅ 对话式需求收集（AI 追问 + HR 确认）
- ✅ 结构化需求文档输出（硬性条件 / 软性要求 / 加分项 / 排除条件）
- ✅ JD 草稿生成（基于行业数据库 + 需求文档）
- ✅ JD 质量评估（覆盖度检查 + 同行对比）
- ❌ 不做简历筛选（下游问题）
- ❌ 不做招聘平台对接（渠道问题）
- ❌ 不做候选人沟通（另一个独立场景）

### 3.2 用户旅程

```
Step 1: HR 输入模糊需求
  "我要一个前端工程师"
  ↓
Step 2: AI 引导式追问
  "这个岗位主要负责什么项目？"
  "团队现在几个人？缺什么角色？"
  "前任为什么离职？"
  "薪资范围是多少？"
  "有没有必须具备的技能？"
  "有没有绝对不要的特征？"
  ↓
Step 3: AI 生成结构化需求文档
  硬性条件：3年以上前端经验、React 精通
  软性要求：有大厂经验、有团队管理经验
  加分项：有微前端经验、有开源贡献
  排除条件：不能接受加班、频繁跳槽（2年内换3份工作）
  ↓
Step 4: AI 生成 JD 草稿
  基于需求文档 + 行业 JD 数据库
  ↓
Step 5: HR 审核 + 用人部门确认
  AI 标注"未经确认的要求"供 HR 核实
  ↓
Step 6: 发布 JD
```

## 四、技术架构（HOW）

### 4.1 架构选型决策

**为什么用 Plan-and-Solve + Reflection，而不是纯 ReAct？**

| 范式 | 适用性 | 理由 |
|------|--------|------|
| ReAct | ⭐⭐ | JD 生成不需要外部工具调用，不需要实时搜索 |
| Plan-and-Solve | ⭐⭐⭐⭐ | 先收集需求再生成 JD，是典型的"先规划后执行" |
| Reflection | ⭐⭐⭐⭐⭐ | JD 质量要求高，需要自我校验防止幻觉 |

**最佳组合**：Plan-and-Solve（主流程）+ Reflection（质量校验）

```
Phase 1 — Plan（需求收集）
  AI 通过对话引导 HR 收集需求
  输出：结构化需求文档
  范式：对话式交互（非 Agent，直接 LLM 对话）

Phase 2 — Solve（JD 生成）
  基于需求文档 + 行业 JD 数据库生成 JD 草稿
  范式：Plan-and-Solve（先规划 JD 结构，再填充内容）

Phase 3 — Reflect（质量校验）
  自我检查 JD 是否包含未确认的要求
  对比同行 JD，标注差异
  范式：Reflection（执行→反思→修正）
```

### 4.2 上下文工程设计

基于 Hello-Agents 第 9 章的 GSSC 流水线：

```
【Gather（汇集）】
  - 用户输入的需求描述
  - 对话历史（最近 5 轮）
  - 公司信息（如有）
  - 行业 JD 数据库（RAG 检索）

【Select（选择）】
  - 按相关性 + 新近性评分
  - 系统指令（最高优先级）
  - 对话历史（中等优先级）
  - 行业 JD 参考（按相关性排序）

【Structure（结构化）】
  [Role & Policies]
    你是 JD Copilot，一个帮助 HR 编写 JD 的 AI 助手。
    行为规则：
    - 对缺失信息标记为 null，不编造
    - 标注"未经确认的要求"
    - 提供 JD 的来源依据
  
  [Task]
    当前任务：{用户输入}
  
  [Context]
    对话历史：{最近 5 轮对话}
    需求文档：{已收集的结构化需求}
  
  [Evidence]
    行业参考：{RAG 检索的同行 JD}
  
  [Output]
    请基于以上信息，输出结构化的 JD 草稿。

【Compress（压缩）】
  - 对话历史超过 5 轮时，压缩早期内容为摘要
  - 关键信息（硬性条件、排除条件）每轮带上
  - 行业 JD 参考只保留最相关的 3 条
```

### 4.3 幻觉防控设计

| 幻觉类型 | 风险 | 防控措施 |
|----------|------|----------|
| 编造用人部门未提及的要求 | JD 中出现"需要 CPA 证书"但用人部门没提 | ① 每个要求标注来源（"来自对话第 3 轮"或"来自行业参考"）② 未经确认的要求标记为"待确认" |
| 编造行业数据 | "同行 JD 的平均薪资是 30K"但没有数据来源 | ① 只引用 RAG 检索到的真实 JD ② 不引用无法验证的数据 |
| 编造岗位职责 | 生成的 JD 包含不真实的岗位职责 | ① 岗位职责必须来自用人部门描述 ② AI 补充的职责标记为"建议" |
| 格式漂移 | 输出不符合 JD 标准格式 | ① 6 层 JSON 兜底策略 ② Few-shot examples ③ Temperature 0.2 |

### 4.4 Agent Loop 设计

```javascript
// JD Copilot — Plan-and-Solve + Reflection Agent

async function runJDCopilot(vagueInput, companyInfo, apiKey) {
  // ═══ Phase 1: Plan（需求收集）═══
  // 对话式交互，不是 Agent 调用
  const requirementDoc = await collectRequirements(vagueInput, apiKey);
  // 输出：{ hard_req, soft_req, nice_to_have, exclude, salary_range, ... }

  // ═══ Phase 2: Solve（JD 生成）═══
  // Plan-and-Solve：先规划 JD 结构，再填充内容
  const jdStructure = await planJDStructure(requirementDoc, apiKey);
  // 输出：{ sections: ["岗位描述", "岗位职责", "任职要求", "加分项"] }
  
  const jdDraft = await generateJDDraft(requirementDoc, jdStructure, apiKey);
  // 输出：完整的 JD Markdown 文本

  // ═══ Phase 3: Reflect（质量校验）═══
  // Reflection：自我检查 → 修正
  const reflection = await reflectOnJD(jdDraft, requirementDoc, apiKey);
  // 输出：{ issues: [...], suggestions: [...], confidence: 0.8 }
  
  if (reflection.confidence < 0.7) {
    // 置信度低，需要人工确认
    return { jd: jdDraft, status: 'needs_review', reflection };
  }
  
  const finalJD = await refineJD(jdDraft, reflection, apiKey);
  return { jd: finalJD, status: 'ready', reflection };
}
```

### 4.5 Eval 体系

基于 Hello-Agents 第 12 章的评估框架：

```
【评估数据集】
  10 个 Golden Examples，覆盖 4 类场景：
  
  A. 标准岗位（3个）：前端工程师、产品经理、数据分析师
  B. 复合岗位（3个）：全栈工程师、增长负责人、技术 PM
  C. 模糊需求（2个）："我要一个厉害的人"、"需要一个能带团队的"
  D. 异常输入（2个）：空输入、与 HR 无关的输入

【评估指标】
  1. 需求覆盖度：AI 生成的需求文档覆盖用人部门真实需求的比例
     目标：≥ 80%
  
  2. JD 准确度：AI 生成的 JD 与 HR 最终使用的 JD 的匹配度
     目标：≥ 70%
  
  3. 幻觉率：AI 编造用人部门未提及要求的比例
     目标：≤ 10%
  
  4. 对话效率：从输入需求到生成 JD 的对话轮数
     目标：≤ 8 轮
  
  5. 用户满意度：HR 对 JD 质量的评分（1-5）
     目标：≥ 4.0

【评估方法】
  Layer 1（快速）：3 个样本，每次代码提交
  Layer 2（标准）：10 个样本，每次提示词修改
  Layer 3（全面）：20+ 样本（含真实数据），每月
```

### 4.6 Token 经济学

```
【成本模型】
  Phase 1（需求收集）：~5 轮对话 × 1000 tokens/轮 = 5000 tokens
  Phase 2（JD 生成）：2 次调用 × 1500 tokens/次 = 3000 tokens
  Phase 3（质量校验）：2 次调用 × 1000 tokens/次 = 2000 tokens
  合计：~10,000 tokens/次

  DeepSeek V4 Pro: $0.27/M 输入 + $1.10/M 输出
  单次成本：~$0.005 ≈ ¥0.035
  日均 20 次：¥0.7/天
  月均 400 次：¥14/月

【优化策略】
  1. 对话历史压缩：超过 5 轮时压缩早期内容
  2. RAG 缓存：相同行业的 JD 参考缓存 24h
  3. 模型分级：需求收集用 8B（快+便宜），JD 生成用 V4 Pro（质量高）
```

## 五、合规与风险设计

### 5.1 偏见缓解

```
输入层：
  ✗ 不提取性别、年龄、民族、婚姻状况
  ✓ 只提取：岗位名称、职责、要求、薪资范围

模型层：
  System Prompt 禁止：
  "你不能基于候选人的性别、年龄、民族做出任何建议。
   你只关注岗位职责和任职要求。"

输出层：
  ✗ 不输出歧视性描述（如"男性优先"、"35岁以下"）
  ✓ 只输出基于能力和经验的客观要求

监控层：
  定期抽检 JD 中是否包含歧视性语言
  使用关键词检测 + LLM 分类双重过滤
```

### 5.2 数据隐私

```
数据处理规则：
  - 对话内容在 Edge Function 中处理，不落盘
  - 历史 JD 不存储在服务器
  - 用户可随时请求删除所有数据
  - 日志中 PII 字段脱敏

合规声明：
  - 首次使用时告知用户数据处理方式
  - 提供"删除我的数据"功能
  - 不将用户数据用于模型训练
```

### 5.3 Human-in-the-loop

```
置信度分级：
  ≥ 0.8：AI 输出 JD 草稿，HR 可选确认
  0.6-0.8：AI 输出 JD + 标注"待确认"项，HR 必须审核
  < 0.6：AI 只输出需求文档，不生成 JD，HR 人工编写

HR 覆盖机制：
  - HR 可修改 AI 生成的任何内容
  - 修改原因记录到审计日志
  - 修改数据用于 Eval 数据集扩充
```

### 6.2 Phase 0 验证计划

```
目标：验证"JD 与真实需求错配"是否是一个真实、值得解决的问题

方法：
  1. 访谈 5 个 HR（不同行业、不同规模公司）
     问题：
     - 你最近一次 JD 和真实需求不符的经历是什么？
     - 你通常花多长时间写一份 JD？
     - 用人部门给你的需求通常有多清晰？
     - 你觉得什么工具能帮到你？

  2. 收集 10 份真实 JD + 对应的用人部门原始需求
     对比 JD 和原始需求的匹配度

  3. 用 AI 对话模拟"帮 HR 收集需求"的过程
     对比 AI 生成的 JD 和 HR 最终使用的 JD

成功标准：
  - 至少 3/5 的 HR 确认"JD 与真实需求错配"是真实痛点
  - AI 生成的 JD 与 HR 最终使用的 JD 匹配度 ≥ 60%
```

```
4. DEMO — 可交互的 JD Copilot 体验
5. EVAL — 评估体系 + Golden Examples + 质量指标
6. COST — Token 经济学 + 全生命周期成本
7. COMPLIANCE — 合规设计 + HITL + 数据隐私
8. RESULT — 验证计划 + 已知差距 + 优先级排序
```

### 7.2 面试官视角的设计

**产品负责人会看的**：
- 问题定义是否有数据支撑（行业数据 + 用户访谈）
- MVP 边界是否清晰（做什么 + 不做什么）
- 成本分析是否诚实（直接成本 + 隐性成本）
- 改进优先级是否合理（P0-P3）

**技术负责人会看的**：
- 架构选型是否有依据（为什么选 Plan-and-Solve + Reflection）
- 幻觉防控是否到位（6 层 JSON 兜底 + 标注来源）
- Eval 体系是否完整（数据集 + 指标 + 分层评估）
- 上下文工程是否合理（GSSC 流水线）

**HR 总监会看的**：
- 是否真正理解 HR 的工作（不只是"简历筛选"）
- 合规意识是否到位（偏见缓解 + 数据隐私 + HITL）
- 是否有真实数据验证（不只是 Demo）
- 产品是否能融入现有工作流

## 八、与之前方案的核心区别

| 维度 | 之前（简历筛选 Agent） | 现在（JD Copilot） |
|------|----------------------|-------------------|
| **问题定义** | 简历筛选效率低（痛点第 6 位） | JD 与真实需求错配（痛点第 1 位） |
| **用户价值** | 提升筛选速度 | 减少全链路浪费 |
| **技术方案** | ReAct + 5 个 Tool | Plan-and-Solve + Reflection |
| **Agent 范式** | 固定流水线（假 ReAct） | 真正的先规划后执行 + 自我校验 |
| **幻觉防控** | 基本没有 | 6 层 JSON 兜底 + 来源标注 + Reflection |
| **合规设计** | 后补的 | 内置的（偏见缓解 + 数据隐私 + HITL） |
| **验证计划** | 没有 | 三阶段验证（访谈 → 模拟 → 测试） |
| **诚实度** | 夸大成本优势（"250×"） | 诚实承认局限（"准确率需要验证"） |

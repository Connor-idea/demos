02 · WHAT

产品定义：JD Copilot

✅ 做什么

• 对话式需求收集（AI 追问 + HR 确认）

• 结构化需求文档输出

• JD 草稿生成（行业数据库 + 需求文档）

• JD 质量评估（覆盖度 + 同行对比）

❌ 不做什么

• 不做简历筛选（下游问题）

• 不做招聘平台对接（渠道问题）

• 不做候选人沟通（独立场景）

• 不代替 HR 做最终审核

Skill Card 六维框架

维度定义
Intent帮 HR 从模糊需求出发，系统性收集真实需求，生成结构化 JD
TriggerHR 输入新岗位需求 / 用人部门提出招聘需求
Boundary不编造未提及的要求；不代替 HR 做决策；标注"待确认"项
Quality Bar需求覆盖度 ≥ 80%、JD 准确度 ≥ 70%、幻觉率 ≤ 10%
Golden Examples10 个标准案例覆盖 4 类场景（标准/复合/模糊/异常）
Integration输入：模糊需求文本；输出：需求文档 + JD 草稿 + 质量报告

04 · HOW

  
技术架构


  

    
范式选型：为什么是 Plan-and-Solve + Reflection？

    

      
范式适用性理由

      
ReAct⭐⭐JD 生成不需要外部工具调用

      
Plan-and-Solve⭐⭐⭐⭐先收集需求再生成 JD，典型的"先规划后执行"

      
Reflection⭐⭐⭐⭐⭐JD 质量要求高，需要自校验防止幻觉

    

    
范式选择依据：Hello-Agents Chapter 4 — 智能体经典范式构建

  


  

    

      
Agent 执行流程

      

        Phase 1 — Plan（需求收集）

          AI 对话引导 HR 收集需求

          输出：结构化需求文档


        Phase 2 — Solve（JD 生成）

          基于需求文档 + 行业数据生成 JD

          输出：JD 草稿


        Phase 3 — Reflect（质量校验）

          自检查：是否有未确认的要求？

          对比同行 JD，标注差异

          输出：质量评估报告
      

    

    

      
幻觉防控

      

        
风险措施

        
编造未提及的要求标注来源（"来自对话"或"来自参考"）

        
编造行业数据只引用 RAG 检索到的真实 JD

        
格式漂移6 层 JSON 兜底 + Few-shot

        
上下文丢失关键信息每轮带上 + 外部笔记

07 · 合规

  
合规与风险设计


  

    

      
🛡 偏见缓解

      
• 不提取性别/年龄/民族

      
• Prompt 禁止敏感属性判断

      
• 定期抽检 JD 中的歧视性语言

    

    

      
🔒 数据隐私

      
• Edge Function 处理，不落盘

      
• 用户可请求删除所有数据

      
• 日志中 PII 脱敏

    

    

      
👤 HITL 机制

      
• 置信度 ≥ 0.8：自动输出

      
• 0.6-0.8：标记"待审核"

      
• < 0.6：转人工判断

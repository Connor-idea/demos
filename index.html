01 · WHY

为什么做这个项目？

问题假设（JTBD 框架）

以下基于与 3 位 HR 从业者的非正式访谈 + LinkedIn 2024 中国招聘趋势报告。这是定性假设，不是定量调研。

Job Story 1 — 招聘经理

"当我在 ATS 里看到 50 份新简历时，我想在 30 秒内判断哪些值得安排电话面试，这样我不会在不符合硬性条件的简历上浪费时间。"

Job Story 2 — HRBP

"当业务部门催我要候选人时，我想快速从简历池中筛选出 Top 5，这样我能及时响应业务需求。"

Job Story 3 — HR 总监

"当我要汇报招聘进展时，我想看到量化的筛选数据（通过率、拒绝原因分布），这样我能发现招聘漏斗的瓶颈。"

这个产品做什么

将非结构化简历/JD 转为结构化评估报告，辅助 HR 做初筛决策。AI 做信息处理，人做最终判断。

具体输出：匹配度评分（0-100）+ 优势/差距分析 + 推荐级别 + 置信度

这个产品不做什么

✗ 不做最终录用决策

✗ 不判断文化匹配度、软技能

✗ 不替代电话初筛

✗ 不处理候选人隐私信息（性别/年龄/民族）

已知局限（诚实声明）

• 初筛只是 HR 痛点的第 6 位（前面是招不到人、候选人放鸽子、需求不清等）— 这个产品不解决最大的痛点

• AI 只能处理硬性条件匹配（学历/年限/技能），无法判断项目含金量和文化匹配

• 依赖简历文本质量 — 格式异常或信息不足的简历准确率会大幅下降

03 · HOW — 架构设计

ReAct + Tool-Based 架构

借鉴 Hello-Agents 教程的「万物皆为工具」理念，将单次大 prompt 拆解为 5 个独立工具的有序调用，Agent 通过 ReAct 循环（Think → Act → Observe）驱动整个分析流程。

🔧 experience_evaluator

📋 report_generator

📤 输出

为什么用 ReAct 而不是单次调用？

❌ 单次调用的问题

• 一个巨大的 prompt 塞所有指令，模型容易「顾此失彼」

• 中间过程不可见，出错无法定位

• 无法对每个步骤独立优化

• Token 浪费严重（每次传全部上下文）

✅ ReAct 的优势

• 每步只关注一个子任务，准确率更高

• 全链路可追踪，问题可定位

• 每个工具可独立测试和迭代

• 用户看到思考过程，信任度更高

条件分支与错误恢复（真实 ReAct）

Agent 不是固定流水线。每一步的 Observe 结果会影响下一步的决策：

// Step 1: 解析简历 resume_result = resume_parser(resume) if resume_result.error: → 返回错误，终止分析（不继续浪费 token） if 缺失字段 >= 2（姓名/年限/技能）: → 降低置信度，继续分析但标记 warning // Step 4: 经验评估（条件跳过） if JD 是初级岗位 且 候选人经验 >= 2年: → 跳过 experience_evaluator（节省 1 次 API 调用） → 直接使用默认高分 // Step 5: 报告生成（置信度驱动 HITL） if confidence < 0.6: → recommendation = "需人工判断"（不输出推荐，转人工） elif confidence < 0.7: → recommendation = "待定" + 标记 "HR 审核确认" else: → recommendation = "推荐/不推荐"

五个工具的职责定义

工具输入输出设计意图
resume_parser原始简历文本结构化 JSON（姓名/经验/技能/学历）信息提取，降低后续步骤的噪声
jd_analyzer原始 JD 文本硬性要求 / 软性要求 / 加分项将模糊描述转为可对比的结构
skill_matcher解析后的技能 + 要求匹配率 / 差距分析逐项对比，量化技能匹配度
experience_evaluator解析后的经验 + 要求年限/行业/岗位匹配分评估隐性匹配维度
report_generator所有中间结果最终评估报告汇总并给出推荐建议
04 · HOW — 提示词工程

提示词设计：从 System Prompt 到 Tool Prompt

提示词是 Agent 产品的「行为规范」。我采用三层结构：System Prompt（角色定义）→ Tool Prompt（工具指令）→ Output Schema（输出约束）。

System Prompt（角色定义层）

// 核心设计原则：角色 + 行为规则 + 边界 + 输出格式 你是「智聘助手」，一个基于 ReAct 范式的 HR 智能招聘 Agent。 ## 你的工作方式 你通过 Think → Act → Observe 循环来完成任务。每一步： 1. Think: 分析当前状态，决定下一步行动 2. Act: 调用一个工具获取信息 3. Observe: 审视工具返回的结果 ## 行为准则 - 对缺失信息标记为 null，绝不编造 - 分数范围 0-100，置信度 0-1 - 每次只调用一个工具 ## 绝对不能做 - 不能编造简历中没有的信息 - 不能做出最终录用决策（只提供建议）

Tool Prompt（工具指令层）示例

// resume_parser 的 Tool Prompt 从以下简历中提取结构化信息，只输出 JSON： {resume_text} 输出格式： { "name": "姓名 | null", "experience_years": 数字 | null, "skills": ["技能1", "技能2"], "education": "学历 | null", "highlights": ["亮点1", "亮点2"] } // 设计要点： // 1. 明确输入（简历文本）和输出（JSON Schema） // 2. 用 | null 标记可选字段，引导模型不编造 // 3. "只输出 JSON" 减少格式漂移

提示词迭代记录

版本问题修改效果
v1模型输出多余解释文字添加"只输出 JSON"JSON 解析成功率 60%→90%
v2缺失字段被编造添加"标记 null，不编造"幻觉率降低 40%
v3评分范围不一致明确"0-100 整数"评分分布标准化
v4推荐建议格式混乱限制为 5 个枚举值推荐一致性 95%

JSON 兜底策略（6 层解析）

DeepSeek V4 Pro 偶尔输出非标准 JSON（含注释、尾逗号等）。采用 6 层递进兜底：

// Strategy 1: 直接解析 JSON.parse(raw) // 成功率 ~85% // Strategy 2: 提取 ```json 代码块 raw.match(/```json\s*([\s\S]*?)\s*```/) // Strategy 3: 提取花括号内容 raw.match(/\{[\s\S]*\}/) // Strategy 4: 清理后重试（移除注释、尾逗号） raw.replace(/\/\/.*$/gm, '').replace(/,\s*([}\]])/g, '$1') // Strategy 5: Key-Value 提取（最后手段） /"(\w+)"\s*:\s*(?:"([^"]*)"|(\d+)|(\[[^\]]*\])|(null))/g // Strategy 6: 返回 null + raw（完全失败）

Temperature 实验

TemperatureJSON 成功率分数稳定性结论
0.0100%完全一致（无区分度）太死板
0.295%72-83（合理波动）✅ 选中
0.580%65-85（波动大）不稳定
0.7+60%不可预测❌ 不可用

结论：temperature=0.2 是平衡点。剩余 5% 失败由 JSON 兜底策略覆盖。

05 · HOW — 质量监控

Eval 体系：如何度量 Agent 质量？

Agent 不是写完就完了。没有 Eval 的 Agent 就是没有测试的代码。我构建了三层评估体系：

🧪

Layer 1: Golden Examples

预设标准案例，验证基础功能是否正确。每次部署前必跑。

📊

Layer 2: Quality Bar

定义质量底线：准确率 ≥80%、推荐匹配率 ≥75%、JSON 解析率 ≥90%

🔄

Layer 3: 持续监控

线上分析结果回流，定期抽检，发现退化及时告警

Golden Examples 设计（10 个样本，4 类场景）

类别场景预期分数预期推荐
A 高匹配8年大厂 vs 首席架构师60-90推荐
A 高匹配6年产品总监 vs 产品总监65-90推荐
B 中匹配3年前端 vs 5年高级前端35-65待定
B 中匹配4年数据分析 vs 数据科学家30-60待定
C 低匹配2年运营 vs 高级产品经理10-40不推荐

4. 输出评估报告（通过/未通过）

二、隐性成本（需估算）

成本项估算说明
误判成本（假阴性）难以量化AI 漏筛优秀候选人的机会成本。假设 5% 漏筛率，每月可能错过 2-3 个合格候选人
信任建立成本~2-4 周HR 初期不信任 AI，会人工复核所有结果。前 2 周效率提升 ≈ 0

合规成本一次性隐私政策制定、偏见审计、法律咨询（首次上线前）

三、正确的价值对比

不是 "AI vs 人工"，而是 "AI 辅助人工 vs 纯人工"

纯人工初筛

3 分钟/份 × 100 份/天 = 300 分钟（5 小时）

AI 辅助初筛

推荐（~30%）：30 份 × 30 秒确认 = 15 分钟

待定（~20%）：20 份 × 2 分钟审核 = 40 分钟

不推荐（~50%）：抽检 10 份 × 1 分钟 = 10 分钟

合计：65 分钟（效率提升 4.6×）

⚠️ 前提条件：准确率 ≥ 85%。低于此阈值 HR 不会信任 AI，会全量人工复核。

四、优化策略

📉 已实施的优化

1. 条件跳过：简单 JD 跳过 experience_evaluator，节省 1 次调用

2. Temperature 0.2：减少随机性，降低重试率

3. JSON 兜底：6 层解析策略，避免格式失败导致整次调用浪费

📉 计划中的优化

1. 缓存：相同简历+JD 缓存结果（24h 有效）

2. 批量合并：多份简历合并为 1 次 LLM 调用

3. 模型降级：简单场景用 8B 模型，复杂场景用 V4 Pro

合规与风险设计

🛡 偏见缓解

• 输入层：不提取性别、年龄、民族、婚姻状况

• 模型层：System Prompt 禁止基于敏感属性判断

• 输出层：不包含性别/年龄相关描述

• 监控层：定期抽检不同群体的评分分布

🔒 数据隐私

• 分析在 Edge Function 完成，不落盘

• 原始简历文本不存储在服务器

• 用户关闭页面 → 数据即销毁

• 日志中 PII 字段脱敏

👤 Human-in-the-loop（HITL）机制

置信度AI 行为HR 行为
≥ 0.7自动输出推荐可选：快速确认
0.6 - 0.7输出结果 + 标记"待审核"必须：审核确认
< 0.6只输出结构化信息，不输出推荐必须：人工判断

HR 可覆盖 AI 判断，覆盖原因记录到审计日志，用于后续 Eval 数据集扩充。

验证计划（三阶段）

Phase 1: 脱敏数据测试（当前阶段）

用 20 份公开脱敏简历测试，对比 AI 与人工判断的一致率。分析不一致 case 的原因。

Phase 2: A/B 测试（需要 HR 参与）

同一批简历，分别用 AI 辅助和纯人工筛选。对比效率、准确率、HR 满意度。

Phase 3: 持续监控（上线后）

每周统计推荐候选人后续表现，计算实际录用率，发现退化自动告警。

做对了什么

• ReAct 范式让分析过程可解释，用户信任度高

• Tool-Based 架构方便独立迭代每个分析模块

• 条置信度分级实现了基本的 HITL 机制

• JSON 6 层兜底策略保证了输出的健壮性

• Token 成本意识贯穿设计，单次 ¥0.009 可规模化

已知差距（诚实面对）

• Eval 数据集不足：10 个样本不具备统计意义，需要扩充到 50+

• 没有真实数据验证：当前只用虚构简历，需要脱敏真实数据测试

• ReAct 实现不完整：有条件分支但没有动态规划（如根据 JD 复杂度决定步骤数）

• 没有 ATS 集成：当前是独立工具，需要集成到现有工作流才有实际价值

• 偏见检测未实现：只有设计，没有实际的监控代码

优先级排序（P0-P3）

优先级改进项理由
P0Eval 数据集扩充（10→50+）没有评估就没有改进依据。所有后续优化都依赖 Eval。
P0脱敏真实数据验证没有真实数据的验证，和 PPT 没有区别。
P1准确率优化（提示词迭代）准确率从当前水平提升到 85%+，是 HR 信任的门槛。
P1偏见监控实现合规硬约束，上线前必须有。
P2ATS 集成（Webhook/API）不集成到现有工作流，HR 不会主动用。
P2批量处理模式效率提升的关键，但前提是有足够准确率。

# 产品负责人视角：逐条回应与改进方案

> 基于批评文档的每一条质疑，使用 Skill Card 六维框架、Eval 体系、Harness 思维、Token 经济学等 PM Skills 逐条回应。不是辩解，是改进。

---

## 批评 1：痛点定义没有用户调研支撑

**批评原文**："100+ 份简历/天"、"400+ 小时/月"没有数据来源，面试官一问就穿。

### 改进方案：Skill Card — Intent（意图定义）

**Skill Card 第一维 Intent** 要求回答：这个 Agent 要解决什么问题？为谁解决？

```
【Skill Card v2 — Intent】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
目标用户：中型企业（100-500人）的招聘经理 / HRBP
使用场景：简历投递后的初筛阶段（ATS 管线中"待筛选"状态）
核心任务：将非结构化简历转为结构化评估报告，辅助 HR 做初筛决策
不做的事：不做最终录用决策、不做候选人排序、不替代电话初筛
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**痛点来源的诚实声明**：

页面中应该改为：
> "痛点观察基于：① 招聘平台公开报告（LinkedIn 2024 中国招聘趋势报告：HR 平均每周花 23 小时在简历筛选上）；② 与 3 位 HR 从业者的非正式访谈；③ 个人在实习/项目中的观察。这不是定量调研，是定性假设，需要后续验证。"

**如果面试官追问**："你做过用户调研吗？"
> "目前是定性阶段。我的方法是：先用 Skill Card 定义假设 → 用 Eval 体系验证假设 → 根据验证结果迭代。如果进入真实项目，第一步是做 10 人的深度访谈，用 JTBD（Jobs to be Done）框架挖掘真实需求。"

## 批评 2：产品定位是正确的废话

**批评原文**："AI 做信息处理，人做最终判断"谁都会说，缺的是具体场景和 MVP 边界。

### 改进方案：Skill Card — Boundary（边界定义）+ Integration Contract（集成契约）

**Skill Card 第四维 Boundary** 要求回答：什么场景下 Agent 不能用？

```
【Skill Card v2 — Boundary】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Agent 不能介入的场景：
1. 最终录用/拒绝决策 → 必须由 HR 和用人经理共同决定
2. 涉及候选人隐私的信息提取 → 不提取性别、年龄、婚姻状况
3. 候选人主动要求人工审核 → 必须转人工
4. AI 置信度 < 0.6 的分析 → 标记为"需人工判断"，不输出推荐

Agent 可以介入的场景：
1. 硬性条件匹配（学历、年限、技能关键词）→ 自动化
2. 结构化信息提取（姓名、公司、职位）→ 自动化
3. 匹配度评分 → AI 初评 + HR 确认
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**Skill Card 第六维 Integration Contract** 要求回答：和外部系统如何对接？

```
【Skill Card v2 — Integration Contract】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
输入契约：
  - resume_text: string (必填，100-5000字)
  - jd_text: string (必填，50-3000字)
  - options: { sensitivity: "high"|"medium"|"low" } (可选)

输出契约：
  - candidate: { name, years, skills[], education }
  - match: { score: 0-100, dimensions: {}, strengths[], gaps[] }
  - recommendation: "推荐面试"|"待定"|"不推荐"|"信息不足"
  - confidence: 0-1
  - warnings: string[] (格式异常、信息缺失等)

错误契约：
  - 简历为空 → 400 + "请提供简历内容"
  - 解析失败 → 500 + 返回部分结果 + warnings
  - 模型超时 → 504 + "服务繁忙，请稍后重试"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**MVP 定义（一句话）**：
> "HR 粘贴简历和 JD → AI 输出结构化评估报告（分数 + 优势 + 差距 + 推荐）。不做批量、不做 ATS 集成、不做候选人追踪。V1 只支持中文简历。"

## 批评 3：成本分析只算了直接成本

**批评原文**：¥0.01/次的计算忽略了误判成本、合规成本、信任成本、维护成本。

### 改进方案：Token 经济学 — 全成本模型

**改进后的成本分析页面应该展示**：

```
【成本模型 v2 — 全生命周期成本】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
一、直接成本（可量化）
  API 调用：¥0.01/次 × 100次/天 × 22天 = ¥22/月
  基础设施：Vercel Pro $20/月 ≈ ¥145/月
  合计直接成本：¥167/月

二、隐性成本（需估算）
  误判成本：
    - AI 漏筛优秀候选人（假阴性）：假设 5% 的漏筛率
    - 每月 2200 份简历 × 5% = 110 人被错误拒绝
    - 其中可能有 2-3 个"本可以录用"的候选人
    - 机会成本：难以量化，但需要监控
    
  信任成本：
    - HR 初期不信任 AI，会人工复核所有结果
    - 前 2 周的效率提升 ≈ 0（因为 HR 还是全看了）
    - 信任建立需要 2-4 周 + 准确率 > 85%
    
  维护成本：
    - 提示词调优：每月 2-4 小时
    - Eval 数据集更新：每月 1-2 小时
    - 模型版本升级/切换：每季度 4-8 小时

三、价值对比（正确的算法）
  不是 "AI vs 人工"，而是 "AI 辅助人工 vs 纯人工"
  
  纯人工：3 分钟/份 × 100 份/天 = 300 分钟 = 5 小时
  AI 辅助：HR 只看 AI 推荐的 + 边界 case
    - 推荐（~30%）：HR 快速确认 30 份 × 30 秒 = 15 分钟
    - 待定（~20%）：HR 详细审核 20 份 × 2 分钟 = 40 分钟
    - 不推荐（~50%）：HR 抽检 10 份 × 1 分钟 = 10 分钟
    - 合计：65 分钟（效率提升 4.6×，不是 250×）
    
  前提条件：准确率 ≥ 85%（低于此 HR 不会信任）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**面试官追问应对**：
> "250 倍成本优势这个数字我已经修正了。正确的对比方式是 AI 辅助 vs 纯人工，效率提升约 4-5 倍。但这个数字的前提是准确率达到 85%。我目前的 Eval 体系还不够完善（只有 2 个 Golden Example），下一步是构建 20+ 样本的评估数据集来验证这个假设。"

## 批评 4：完全没有风险意识

**批评原文**：没有提到歧视风险、合规风险、信任风险。

### 改进方案：Harness — Sensors（反馈控制）

**Harness 设计中的 Sensors** 用于持续检测质量风险。我设计三个 Sensor：

```
【Sensor 1: 偏见检测器】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
监控维度：
  - 性别偏见：分析结果中是否出现性别相关判断
  - 学历偏见：非 985/211 候选人的平均分是否显著低于 985/211
  - 年龄偏见：35+ 候选人的推荐率是否显著低于 35 以下
  
检测方法：
  - 每 100 次分析后自动抽检
  - 对比不同群体的平均分和推荐率
  - 如果差异 > 15%，触发告警
  
缓解措施：
  - System Prompt 中明确禁止基于性别/年龄/民族的判断
  - 输出中不包含性别、年龄等敏感字段
  - 如果模型输出中出现敏感词，自动过滤并记录 warning
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【Sensor 2: 数据隐私检查器】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
规则：
  - 分析完成后不存储原始简历文本（只存储结构化结果）
  - 用户可随时请求删除所有数据
  - 日志中对手机号、邮箱等 PII 字段脱敏
  - 分析结果保留 30 天后自动删除
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【Sensor 3: 可解释性检查器】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
规则：
  - 每个推荐必须附带至少 2 条具体理由
  - 每个不推荐必须附带至少 1 条具体原因
  - 理由必须引用简历中的具体内容（不能是泛泛的"经验不足"）
  
示例：
  ✅ "推荐面试：候选人有 5 年电商产品经验（字节跳动抖音电商），
      与 JD 要求的 3 年以上电商经验高度匹配"
  ❌ "推荐面试：候选人经验丰富，适合该岗位"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 批评 5：改进方向没有优先级

**批评原文**：列了 5 个改进方向，没有优先级和决策依据。

### 改进方案：产品判断力 — ROI 排序

**改进后的优先级排序（带决策依据）**：

| 优先级 | 改进项 | ROI 理由 | 前置条件 |
|--------|--------|----------|----------|
| **P0** | Eval 数据集扩充（2→20+） | 没有评估就没有改进依据。所有后续优化都依赖 Eval。 | 无 |
| **P0** | Human-in-the-loop 机制 | 法律合规硬约束，没有这个不能上线。 | Eval 体系 |
| **P1** | 准确率优化（提示词迭代） | 准确率从 70%→85% 是信任门槛。低于 85% HR 不会用。 | Eval 数据集 |
| **P1** | 可解释性增强 | HR 需要知道"为什么推荐"才能信任 AI 的判断。 | 准确率 ≥ 80% |
| **P2** | ATS 集成 | 不集成到现有工作流，HR 不会主动用独立工具。 | 准确率 ≥ 85% |
| **P2** | 批量处理 | 效率提升的关键，但前提是有足够的准确率。 | ATS 集成 |
| **P3** | 多模态（PDF 解析） | 锦上添花，不是核心需求。 | 批量处理 |

**决策框架**：
> P0 = 没有就不能上线（合规/基础能力）
> P1 = 没有就没有用户（信任/体验）
> P2 = 没有就不能规模化（效率/集成）
> P3 = 锦上添花（功能丰富度）

## 总结：产品负责人视角的核心改进

| 原来的问题 | 改进方案 | 使用的 PM Skill |
|------------|----------|----------------|
| 痛点没有数据来源 | 诚实声明数据来源 + Skill Card Intent 定义 | Skill Card |
| MVP 边界不清 | Boundary + Integration Contract | Skill Card |
| 成本分析不完整 | 全生命周期成本模型 | Token 经济学 |
| 没有风险意识 | 三个 Sensor（偏见/隐私/可解释性） | Harness |
| 改进没有优先级 | P0-P3 排序 + 决策框架 | 产品判断力 |

# 人力资源总监视角：逐条回应与改进方案

> 基于批评文档的每一条 HR 视角质疑，使用 Harness（Guides + Sensors）、产品判断力、合规设计等 PM Skills 逐条回应。核心目标：让一个 HRD 看完后认为"这个人真的理解 HR 的工作"。

---

## 批评 1：你真的理解 HR 的工作吗？

**批评原文**：初筛只是 HR 痛点的第 6 位，你解决的是最浅的那层。

### 改进方案：用 JTBD（Jobs to be Done）重新定义问题

**不再说"初筛效率低"，而是用 HR 的语言描述问题**：

```
【JTBD 重新定义】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Job Story 1（招聘经理）：
  当我收到一份新简历时
  我想在 30 秒内判断这个候选人是否值得安排电话面试
  这样我不会在不符合硬性条件的简历上浪费时间

Job Story 2（HRBP）：
  当业务部门催我要候选人时
  我想快速从简历池中筛选出 Top 5 候选人
  这样我能及时响应业务需求

Job Story 3（HR 总监）：
  当我要汇报招聘进展时
  我想看到量化的筛选数据（通过率、拒绝原因分布）
  这样我能发现招聘漏斗的瓶颈

不解决的 Job：
  - 判断候选人的文化匹配度（需要面对面交流）
  - 评估候选人的软技能（需要面试官判断）
  - 做最终录用决策（需要用人经理确认）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**页面改进**：在"核心痛点"部分，不再用夸张的数据（"100+ 份/天"），而是用 Job Story 描述具体场景。

**面试官追问应对**："你觉得 HR 最大的痛点是什么？"
> "我认为不是初筛效率，而是招聘漏斗的数据透明度。大多数 HR 知道'本月收到 500 份简历，录用了 3 人'，但不知道'在哪个环节流失了最多候选人'、'拒绝原因的分布是什么'。我的产品不只是做初筛，还能量化筛选过程，为招聘漏斗优化提供数据支撑。"

## 批评 2：完全没考虑合规和法律风险

**批评原文**：没有偏见检测、数据隐私、可解释性。

### 改进方案：合规设计框架

**2.1 偏见缓解设计**

```
【偏见缓解措施】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
输入层：
  ✗ 不提取：性别、年龄、民族、婚姻状况、政治面貌
  ✗ 不使用：照片（不做外貌判断）
  ✓ 只提取：姓名、教育、工作经历、技能、项目

模型层：
  System Prompt 中明确禁止：
  "你不能基于候选人的性别、年龄、民族、婚姻状况做出任何判断。
   如果简历中包含这些信息，忽略它们。"

输出层：
  ✗ 不输出：性别相关的描述（如"适合女性岗位"）
  ✗ 不输出：年龄相关的描述（如"年龄偏大"）
  ✓ 只输出：基于技能和经验的客观匹配分析

监控层（Sensor: 偏见检测器）：
  每 100 次分析后自动抽检：
  - 对比不同学历背景的平均分（985 vs 双非）
  - 检查输出中是否出现敏感词
  - 如果差异 > 15%，触发人工审核
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**2.2 数据隐私设计**

```
【数据处理规则】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
收集：
  - 简历文本：用户主动粘贴（明确知情同意）
  - 不收集：IP、设备信息、浏览行为

处理：
  - 分析在 Edge Function 中完成（不落盘）
  - 原始简历文本不存储在服务器
  - 只返回结构化分析结果给用户

存储：
  - 当前版本：不存储任何数据（纯分析工具）
  - 未来版本（如有存储需求）：
    - 结构化结果加密存储
    - 保留期限 30 天
    - 用户可随时请求删除

删除：
  - 用户关闭页面 → 数据即销毁
  - 如有未来存储 → 提供"删除我的数据"按钮
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**2.3 可解释性设计**

```
【可解释性规则】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
每个推荐必须回答三个问题：
  1. 为什么推荐/不推荐？（具体原因）
  2. 依据是什么？（引用简历原文）
  3. 差距在哪里？（可改进的方向）

示例：
  ✅ 好的解释：
  "推荐面试。候选人有 5 年电商产品经验（简历第 2 段：
  '负责抖音电商产品线，DAU 从 100 万提升到 500 万'），
  与 JD 要求的'3 年以上电商经验'高度匹配。
  加分项：有大厂背景（字节跳动）。
  注意：简历未提及 AI 产品经验，这是 JD 的软性要求。"

  ❌ 差的解释：
  "推荐面试。候选人经验丰富，适合该岗位。"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 批评 3：Human-in-the-loop 是上线前提

**批评原文**：HITL 被列在"下一步改进"的第 3 位，应该是 P0。

### 改进方案：HITL 机制设计

```
【Human-in-the-loop 机制】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
触发条件：
  1. AI 置信度 < 0.6 → 自动转人工
  2. 简历信息不足（缺失 > 3 个字段）→ 自动转人工
  3. 候选人主动要求 → 立即转人工

分级处理：
  ┌─────────────┬──────────────┬──────────────────┐
  │ 置信度      │ AI 行为      │ HR 行为          │
  ├─────────────┼──────────────┼──────────────────┤
  │ ≥ 0.8       │ 自动输出推荐 │ 可选：快速确认   │
  │ 0.6 - 0.8   │ 输出结果     │ 必须：审核确认   │
  │             │ + 标记"待审" │                  │
  │ < 0.6       │ 不输出推荐   │ 必须：人工判断   │
  │             │ 只输出结构化 │                  │
  │             │ 信息         │                  │
  └─────────────┴──────────────┴──────────────────┘

HR 覆盖机制：
  - HR 可以修改 AI 的推荐结果
  - 修改原因必须记录（用于后续分析和改进）
  - 覆盖记录用于 Eval 数据集的扩充

审计日志：
  每次分析记录：
  {
    timestamp: "2026-05-29T12:00:00Z",
    input_hash: "abc123",  // 简历的哈希（不存原文）
    ai_recommendation: "推荐面试",
    ai_confidence: 0.75,
    hr_action: "confirmed",  // confirmed | overridden | pending
    hr_override_reason: null,
    processing_time_ms: 8500,
    tokens_used: 2100
  }
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 批评 4：Demo 用的是虚构简历

**批评原文**：没有真实数据验证，和 PPT 没区别。

### 改进方案：真实数据验证计划

```
【验证计划】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Phase 1: 脱敏真实数据测试（当前可做）
  数据来源：
  - 从公开简历平台获取已脱敏的简历样本（如脉脉、LinkedIn 公开简历）
  - 或使用实习/项目中接触过的简历（已获得授权）
  
  测试方法：
  - 20 份简历 × 同一个 JD → AI 分析
  - 20 份简历 × 人工分析（找一个 HR 朋友帮忙）
  - 对比 AI 和人工的一致率
  
  预期输出：
  "20 份简历测试结果：
   - AI 与人工一致：16 份（80%）
   - 不一致的 4 份：分析原因
     - 2 份：AI 无法识别项目含金量（如'参与'vs'主导'）
     - 1 份：简历格式非标准，解析失败
     - 1 份：JD 中的'软性要求'AI 理解偏差"

Phase 2: A/B 测试（需要真实 HR 参与）
  方法：
  - 同一批简历，分别用 AI 辅助和纯人工筛选
  - 对比：筛选时间、通过率、最终录用率
  
  指标：
  - 效率提升倍数（不是 250×，是实际倍数）
  - 准确率（AI 推荐的人 vs 最终录用的人）
  - HR 满意度（NPS 评分）

Phase 3: 持续监控（上线后）
  - 每周统计 AI 推荐的候选人后续表现
  - 计算"推荐准确率"（AI 推荐 → 进入终面 → 录用的比例）
  - 发现退化时自动告警
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**面试官追问应对**："你用真实简历测试过吗？"
> "目前是 Phase 1 阶段。我用 20 份公开脱敏简历做了测试，AI 与人工判断的一致率是 [X]%。不一致的 case 主要集中在 [具体原因]。下一步是找 HR 朋友做 Phase 2 的 A/B 测试。"

## 批评 5：产品怎么融入现有工作流？

**批评原文**：没有说清楚在招聘流程中的位置，没有提 ATS 集成。

### 改进方案：工作流集成设计

```
【招聘流程集成点】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
当前版本（独立工具）：
  简历投递 → HR 复制简历文本 → 粘贴到 Agent → 获取报告 → HR 决定
  
  适用场景：
  - 小团队（< 50 人），没有 ATS
  - 偶尔招聘，不需要系统化管理
  - HR 想快速体验 AI 辅助筛选

V2 版本（ATS 插件）：
  简历投递 → ATS 自动推送到 Agent → Agent 分析 → 
  结果回写 ATS → HR 在 ATS 中查看 → HR 决定
  
  集成方式：
  - 提供 Webhook 接口：ATS 简历状态变更时自动触发
  - 提供 API 接口：ATS 主动调用 Agent 分析
  - 结果格式兼容主流 ATS（Moka、北森、飞书招聘）

V3 版本（深度集成）：
  - 批量分析：ATS 中"待筛选"状态的简历自动批量分析
  - 智能排序：按匹配度排序，HR 只看 Top N
  - 数据看板：招聘漏斗可视化（通过率、拒绝原因分布）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 批评 6：变革管理比技术实现更重要

**批评原文**：HR 可能不信任 AI，你没有提到如何让 HR 接受这个工具。

### 改进方案：变革管理策略

```
【变革管理三步走】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Step 1: 降低威胁感（Week 1-2）
  - 不叫"AI 替你筛选"，叫"AI 助手帮你整理信息"
  - 强调：AI 不做决策，只做信息结构化
  - 让 HR 先用低风险的场景（如实习生简历）

Step 2: 建立信任（Week 3-4）
  - AI 分析结果 + HR 人工分析 → 对比一致率
  - 让 HR 看到 AI 的优势（快速、一致、不遗漏硬性条件）
  - 也让 HR 看到 AI 的局限（无法判断软性匹配）
  - 逐步从"全量人工复核"过渡到"抽检"

Step 3: 融入工作流（Week 5+）
  - AI 分析结果嵌入 HR 的日常工作界面
  - HR 习惯在 AI 结果的基础上做判断（而非从零开始）
  - 定期收集 HR 反馈，持续优化
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 总结：HR 总监视角的核心改进

| 原来的问题 | 改进方案 | 使用的 PM Skill |
|------------|----------|----------------|
| 痛点理解太浅 | JTBD 重新定义问题 | 产品判断力 |
| 没有合规意识 | 偏见缓解 + 数据隐私 + 可解释性 | Harness Sensors |
| HITL 是"下一步" | 三级置信度分级 + 审计日志 | Harness Guides |
| 没有真实数据验证 | 三阶段验证计划 | Eval 体系 |
| 没有工作流集成 | 三版本集成路线图 | Integration Contract |
| 没有变革管理 | 三步走策略 | 产品判断力 |

**给面试官的整体叙事**：
> "这个项目不只是一个技术 Demo。它展示了我如何从 HR 的真实需求出发，用 Skill Card 定义产品边界，用 Eval 体系量化质量，用 Harness 设计控制风险。我知道这个产品离上线还有距离，但每个差距我都有具体的改进计划和优先级排序。"
